3. Two decisions the author flagged for the client

The client gave four reference distances (2/4/6/8m) but not the exact edges between zones, so the code splits the difference — placing the boundaries at the midpoints: 3m, 5m, and 7m. It also spells out exactly how “both buzzers together” works at close range: if either sensor detects something within the CLOSE zone, both buzzers switch to the fast CLOSE pattern, even if the other sensor itself isn't reading anything close. Both are written as single, easy-to-move constants in case testing shows they need adjusting.

4. Why digitalWrite() instead of tone()

Arduino's built-in tone() function can only drive one pin at a time on this chip — calling it for a second buzzer would silently cut off the first. Since the CLOSE zone needs both buzzers sounding at once, the sketch pulses each buzzer pin on and off manually with digitalWrite() instead, which has no such limit. That only works because both buzzers are active buzzers (they sound as soon as they're powered), matching the hardware on this site. The last line is a reminder to double-check pin numbers against the physical build — left buzzer on D4, right buzzer on D5, exactly as wired in the diagram above.

6. Turning the beep-pattern spec into numbers

SENSOR_BAUD confirms the 9600 baud rate both sensors must already be set to. STALE_TIMEOUT_MS is a small safety net: if a sensor stops giving valid readings for less than 400ms, the code treats it as a brief hiccup rather than instantly going silent (more on that in section 11). The four ZONE_..._MAX_CM constants are the exact numeric boundaries from section 2 — 300cm, 500cm, 700cm, and 800cm — turning “3m / 5m / 7m / 8m” into the centimeter values classifyZone() actually compares against.

const int ZONE_NEAR_MAX_CM  = 500;  // 301-500cm (3-5m)   -> NEAR

const int ZONE_FAR_MAX_CM   = 800;  // 701-800cm (7-8m)   -> FAR

7. The timing behind each zone's beep pattern

Each zone's rhythm is just numbers of milliseconds. FAR is a short 60ms pulse followed by a long 1500ms pause. MID beeps for 70ms with 220ms gaps, repeated for a burst of exactly 5 beeps (MID_BURST_COUNT), then pauses 1200ms before the burst repeats. NEAR doesn't have one fixed gap — it defines the gap at each edge of the zone (220ms at 5m, matching MID's pace, down to 80ms at 3m, approaching CLOSE's pace) and interpolates between them, which is what produces the “smoothly speeds up” effect. CLOSE is the fastest and simplest: a 40ms pulse and a 40ms gap, repeating continuously.

8. Turning a distance into a zone

Zone is a small label for which of the four zones a reading falls into, plus ZONE_NONE for out of range. classifyZone() is a straightforward staircase: 0 or less isn't a real reading, so it's ZONE_NONE; up to 300cm is CLOSE; up to 500cm is NEAR; up to 700cm is MID; up to 800cm is FAR; anything beyond that falls through to ZONE_NONE, meaning silence.

// ---------------- ZONE STATE MACHINE ----------------
enum Zone { ZONE_NONE, ZONE_FAR, ZONE_MID, ZONE_NEAR, ZONE_CLOSE };

Zone classifyZone(int distanceCm) {
  if (distanceCm <= 0)                 return ZONE_NONE;
  if (distanceCm <= ZONE_CLOSE_MAX_CM) return ZONE_CLOSE;
  if (distanceCm <= ZONE_NEAR_MAX_CM)  return ZONE_NEAR;
  if (distanceCm <= ZONE_MID_MAX_CM)   return ZONE_MID;
  if (distanceCm <= ZONE_FAR_MAX_CM)   return ZONE_FAR;
  return ZONE_NONE; // beyond 8m
}

10. Reading one TF-Luna sensor

Each TF-Luna streams its own 9-byte data frame roughly every 10ms. This function listens to one sensor, waits up to 25ms for a full frame (so a slow or missing frame can never freeze the rest of the program), then scans for the two-byte header (0x59, 0x59) marking where a frame starts. Once found, it reads the next 7 bytes and checks them against the sensor's own checksum — the same verification described elsewhere on this site. Only if that checksum matches does it trust the distance, packed into the first two of those bytes (low byte, then high byte, in centimeters). If nothing valid comes through, it returns -1. The last line drains any leftover bytes so the next call starts clean.

// ---------------- SENSOR FRAME READING ----------------
// Adapted from Benewake's own official TFmini-Plus/TF-Luna Arduino routine
// (same 9-byte frame + checksum format the TF-Luna uses), with a short
// bounded wait so one bad or missing frame never stalls the loop.
int readDistance(SoftwareSerial &sensor) {
  sensor.listen();

  unsigned long start = millis();
  while (sensor.available() < 9 && millis() - start < 25) {
    // wait briefly for a fresh 9-byte frame (sensor streams ~every 10ms)
  }

  int distance = -1;

  while (sensor.available() >= 9) {
    if (sensor.read() != 0x59) continue;   // resync: scan until header byte 1 found
    if (sensor.peek() != 0x59) continue;   // header byte 2 must follow immediately
    sensor.read();                          // consume confirmed header byte 2

    uint8_t buf[7];
    for (int i = 0; i < 7; i++) buf[i] = sensor.read();

    uint8_t checksum = 0x59 + 0x59;
    for (int i = 0; i < 6; i++) checksum += buf[i];

    if (checksum == buf[6]) {               // matches Benewake's documented checksum
      distance = buf[0] | (buf[1] << 8);    // low byte + high byte, in cm
    }
    break;
  }

  while (sensor.available() > 0) sensor.read();  // drop leftovers before next call

  return distance;
}

11. Deciding which zone a buzzer should actually be in

This runs once per buzzer, per loop(). First it classifies the raw distance into a zone. If that reading isn't valid, rather than instantly going silent, it holds the last confident zone for up to 400ms (STALE_TIMEOUT_MS) — the “brief hiccup” allowance from section 6. Then comes the cross-side escalation from section 3: if the OTHER sensor is in the CLOSE zone, this buzzer is forced into CLOSE too, regardless of what its own sensor reads — this line is the actual mechanism behind “both buzzers sound together” at close range. Whenever the zone changes, the pattern resets cleanly so a new zone always starts its rhythm from the beginning.

void updateBuzzerZone(BuzzerChannel &ch, int distanceCm, bool otherSideClose) {
  unsigned long now = millis();

  Zone rawZone = classifyZone(distanceCm);

  if (rawZone != ZONE_NONE) {
    ch.lastValidAt = now;
  } else if (now - ch.lastValidAt <= STALE_TIMEOUT_MS) {
    rawZone = ch.zone; // brief gap in valid data - hold the previous zone
  } // else: genuinely no reading for a while - stays ZONE_NONE

  // "Both left and right warn" at the closest range: if the OTHER sensor
  // is in the CLOSE zone, this buzzer escalates to CLOSE too, regardless
  // of what this side's own sensor currently reads.
  Zone effectiveZone = otherSideClose ? ZONE_CLOSE : rawZone;

  if (effectiveZone != ch.zone) {
    // entering a different zone - reset the pattern cleanly
    ch.zone = effectiveZone;
    ch.pulseOn = false;
    ch.burstBeepsDone = 0;
    ch.inBurstPause = false;
    ch.nextEventAt = now;
    digitalWrite(ch.pin, LOW);
  }

12. Staying silent, and pacing every beep

If the zone is ZONE_NONE, the buzzer is switched off and the function returns early — the “beyond 8m or no valid reading: silent” rule. Otherwise, nextEventAt is checked against the current time; if it isn't time for the next beep event yet, the function simply returns. This is what makes the whole system non-blocking — no delay() calls anywhere — so both sensors keep getting read every loop no matter what stage of a beep pattern either buzzer is in.

15. NEAR: beeping that actually speeds up

This is where “smoothly speeds up as the object gets closer” actually happens. constrain() clamps the current distance to somewhere between the CLOSE and NEAR boundaries, and map() converts that clamped distance into a gap length, proportionally, between the two NEAR timing constants from section 7. A reading at the 5m edge uses the slower MID-matching gap; a reading at the 3m edge uses a gap nearly as fast as CLOSE; anything between scales smoothly. The pulse itself flips on and off exactly like FAR and MID, just with this distance-dependent gap.

17. What happens once, at power-on

setup() runs a single time when the device is switched on. It opens a Serial connection for debugging over USB (separate from the sensors' own SoftwareSerial connections), tells both SoftwareSerial objects to start listening at 9600 baud, and sets both buzzer pins to OUTPUT mode with an explicit LOW so neither buzzer makes a sound before the main logic takes over.

}

18. What happens continuously, forever

This is the whole system in five lines. Read the left sensor, then the right sensor. Check whether either one, on its own, is currently reading something in the CLOSE zone. Update each buzzer's state — passing each one both its own sensor's distance and whether the OTHER side is close, exactly the input updateBuzzerZone() needs for the escalation logic in section 11. Then print both readings over Serial for debugging while testing the device. Then it all repeats, as fast as the Arduino can loop.

void loop() {
  int leftDist  = readDistance(leftSensor);
  int rightDist = readDistance(rightSensor);

  bool leftIsClose  = (classifyZone(leftDist)  == ZONE_CLOSE);
  bool rightIsClose = (classifyZone(rightDist) == ZONE_CLOSE);

  updateBuzzerZone(left,  leftDist,  rightIsClose);
  updateBuzzerZone(right, rightDist, leftIsClose);

  Serial.print("L:");
  if (leftDist == -1) Serial.print("--"); else Serial.print(leftDist);
  Serial.print("cm  R:");
  if (rightDist == -1) Serial.print("--"); else Serial.print(rightDist);
  Serial.println("cm");
}
